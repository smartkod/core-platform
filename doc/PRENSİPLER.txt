# Archify burada gerçekten anlamlı

Önceki sorundaki Archify fikrini bu projelerde daha ciddi kullanırdım.

Ama Archify'nin görevi **kod yazmak değil**.

Onu bir tür:

> **AI Architecture Governor**

olarak düşün.

Örneğin sen:

> Stripe ile yıllık abonelik ekle.

diyorsun.

Archify önce:

```text
REQUEST ANALYSIS

Feature:
Annual Subscription

Affected domains:
✓ Billing
✓ Subscription
✓ User
✓ Database

External:
✓ Stripe

Potential changes:
- Subscription model
- Stripe price mapping
- Checkout
- Webhook
- Subscription state machine

Security:
- Stripe webhook signature
- Server-only Stripe secret
- Idempotency

Risk:
HIGH
```

çıkarır.

Sonra:

```text
CHANGE PLAN

1. Database
2. Domain model
3. Stripe integration
4. Webhook
5. Server actions
6. UI
7. Tests
```

der.

**Ancak bundan sonra Coding Agent devreye girer.**

# En önemli dosya: ARCHITECTURE.md

Bunu AI'ın okuyup okuyup değiştirebildiği bir dosya haline getirmem.

Başlangıçta insan tarafından onaylanan **anayasa** gibi düşün.

Örneğin:

```text
# ARCHITECTURE

## Stack

Frontend:
Next.js
React
TypeScript

Database:
PostgreSQL

ORM:
Drizzle / Prisma

Payments:
Stripe

Validation:
Zod

Testing:
Vitest
Playwright

## Rules

1. TypeScript strict mode kullanılacak.

2. Client Component sadece gerektiğinde kullanılacak.

3. Secret key hiçbir zaman client'a gönderilmeyecek.

4. Stripe işlemleri server tarafında yapılacak.

5. Stripe webhook authoritative billing event olarak kabul edilecek.

6. Database değişiklikleri migration ile yapılacak.

7. Feature kodu başka feature'ın internal implementation
   detayına doğrudan erişmeyecek.

8. Business logic UI component içine yazılmayacak.

9. Aynı business logic birden fazla yerde kopyalanmayacak.

10. Yeni dependency eklenmeden önce gerekçesi açıklanacak.

11. Breaking change DECISIONS.md içerisine yazılacak.
```

Bu dosya AI için çok değerli.

---

# DATABASE.md de çok önemli

AI projelerinde en sık bozulan yerlerden biri database.

Örneğin:

```text
User
Subscription
Payment
Invoice
Product
Price
```

arasındaki ilişkiler net tanımlanmalı.

Özellikle Stripe kullanacaksan:

```text
Stripe
   │
   ├── Customer
   │
   ├── Product
   │
   ├── Price
   │
   ├── Checkout Session
   │
   └── Subscription
```

ile senin PostgreSQL modellerinin ilişkisini baştan tanımlamak gerekir.

Örneğin:

```text
users
  ↓
stripe_customer_id

subscriptions
  ↓
stripe_subscription_id

subscription_items
  ↓
stripe_price_id
```

gibi.

**Stripe'ın kendi verisini PostgreSQL'de gereksiz yere kopyalamak da istemeyiz; ama uygulamanın çalışması için gereken local state mutlaka tutulmalı.**

# BILLING.md özellikle ayrı olsun

Stripe nedeniyle bunu genel `ARCHITECTURE.md` içine gömmek yerine ayrı belge yapardım.

Örneğin:

```text
# BILLING

## Source of truth

Stripe:
- payment status
- subscription status
- invoices
- payment events

Application DB:
- local user relationship
- access state
- internal entitlement
- application-specific billing state

## Webhook rules

Stripe webhook:
1. signature verify
2. event idempotency check
3. database transaction
4. update local state
5. return success
```

Bu AI'ın Stripe konusunda **rastgele implementation üretmesini ciddi şekilde azaltır.**

# SECURITY.md

Burada özellikle AI'a sınır koymak gerekir.

```text
# SECURITY

NEVER:

- expose DATABASE_URL
- expose Stripe secret
- expose auth secrets
- trust client supplied user ID
- trust client supplied price
- trust client supplied subscription status
- process Stripe webhook without signature verification
- bypass authorization
- disable CSRF/security mechanisms without documented reason

ALWAYS:

- validate input
- authorize server-side
- use parameterized queries/ORM
- verify webhook signatures
- validate environment variables
- log security-sensitive failures
```

# DECISIONS.md

Bence senin için **çok önemli dosyalardan biri bu.**

AI sürekli:

> "Bunu Prisma yapalım."

sonra:

> "Drizzle daha iyi."

sonra:

> "Supabase kullanalım."

sonra:

> "Server Actions yerine API routes."

diyebilir.

Proje bir süre sonra mimari çöplüğüne döner.

Bunu engellemek için:

```text
# ADR-001

Decision:
Use PostgreSQL.

Status:
Accepted

Reason:
Relational data model and transactional requirements.

Rejected:
MongoDB

Why:
Domain requires relational integrity.
```

ve:

```text
# ADR-002

Decision:
Use Stripe Checkout.

Reason:
Reduce PCI scope and implementation complexity.

Rejected:
Custom card form

Reason:
Unnecessary payment infrastructure responsibility.
```

gibi kararlar tutulur.

AI yeni karar verecekse:

```text
DECISIONS.md
      ↓
mevcut karar
      ↓
çelişiyor mu?
      ↓
evet
      ↓
insan onayı
```

olmalı.

# Bir de CONTRACT.md öneriyorum

Bu doğrudan **AI davranış sözleşmesi** olsun.

Örneğin:

```text
# AI DEVELOPMENT CONTRACT

Before coding:

1. Read ARCHITECTURE.md
2. Read relevant domain documentation
3. Identify affected features
4. Identify existing implementation
5. Do not create duplicate functionality

During coding:

6. Follow existing architecture
7. Keep changes minimal
8. Do not introduce dependencies without justification
9. Do not modify unrelated files
10. Do not silently change database schema

After coding:

11. Run typecheck
12. Run lint
13. Run tests
14. Validate affected flows
15. Report changed files
16. Report architectural impact
17. Report unresolved risks
```

Bu, senin daha önce kullandığın **MASTER DEVELOPER RULES** fikrinin yeni nesil versiyonu olabilir.

# En önemli prensip

Bence senin yeni projelerinde şu döngüyü standart hale getirmeliyiz:

```text
USER REQUEST
     ↓
ARCHIFY
     ↓
UNDERSTAND
     ↓
EXISTING ARCHITECTURE
     ↓
IMPACT ANALYSIS
     ↓
CHANGE PLAN
     ↓
HUMAN APPROVAL*
     ↓
CODER
     ↓
TEST
     ↓
ARCHIFY VALIDATION
     ↓
DONE
```

`*` Her küçük değişiklikte insan onayı gerekmiyor. Archify risk seviyesine göre karar verebilir:

```text
LOW
→ otomatik

MEDIUM
→ plan + otomatik

HIGH
→ plan + kullanıcı onayı

CRITICAL
→ kullanıcı onayı zorunlu
```

Örneğin:

| Değişiklik                    | Risk     |
| ----------------------------- | -------- |
| UI metni                      | LOW      |
| Yeni component                | LOW      |
| Yeni feature                  | MEDIUM   |
| DB migration                  | HIGH     |
| Auth değişikliği              | HIGH     |
| Stripe billing                | HIGH     |
| Database schema redesign      | CRITICAL |
| Payment/security architecture | CRITICAL |

**Bence senin için asıl yatırım Archify skill'inin kendisinden ziyade bu “mimari anayasa + karar kayıtları + risk tabanlı agent workflow” sistemini kurmak olmalı.**

İstersen bir sonraki adımda sana **sıfırdan React/Next.js + PostgreSQL + Stripe projeleri için kullanılabilecek gerçek `ARCHIFY SKILL.md` dosyasını**, ayrıca `ARCHITECTURE.md + CONTRACT.md + SECURITY.md + DATABASE.md + BILLING.md + DECISIONS.md` ile birlikte **AI coding agent'a doğrudan verilebilecek profesyonel bir başlangıç paketi** şeklinde hazırlayabilirim.
